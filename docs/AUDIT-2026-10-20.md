## 1. Health assessment

The application has substantial implemented functionality and existing tests. It needs stronger release discipline and transactional coverage before it can be called release-ready. Main risks are fragmented test execution, stale test/documentation contracts, multiple independent identity systems, and production/preview isolation that cannot be established from source alone.

This is a high-value first batch, not a claim of exhaustive penetration testing or every feature being verified. The repository inventory (421 tracked files, 32 HTML files before this work), root instructions, architecture, database schemas, workflows and relevant feature code were inspected. Attached historical handoffs were used as context, with current source taking precedence. Not every legacy script received a line-by-line review.

The public production homepage returned HTTP 200 on an anonymous GET. This does not establish deployment parity with repository main, backend health, or performance. Production APIs were not used as a mutation test environment.

## 3. Prioritized confirmed findings and fixes

| Severity | Finding and reproduction | Disposition |
| --- | --- | --- |
| High — data integrity | Updating a published deck committed `community_decks` before inserting its version snapshot. A forced history failure returned an error but left the new deck/version committed without history. | **Fixed in branch.** One D1 batch now commits both writes atomically. The snapshot is conditional on the preceding guarded update via `changes()=1`; concurrent stale updates return 409. Verified in SQLite and actual local workerd/D1. |
| Medium — identity handling | Send a malformed/empty explicit Authorization header alongside a valid member-device cookie. Membership authorization silently selected the cookie identity instead of rejecting the supplied credential. | **Fixed in branch.** Explicit invalid credentials return 401 before DB access. Valid bearer and cookie-only paths, tier restrictions and revoked grants retain coverage. This was an identity-selection defect, not a demonstrated unauthenticated privilege escalation. |
| Medium — API robustness | POST JSON `null` to `/api/decks`; the handler dereferenced `parsed.deck` and threw before normal error handling. | **Fixed in branch.** Invalid/non-object envelopes return 400 without DB access. |
| Medium — API robustness | Member request JSON helper accepted null/scalars/arrays; member handlers could dereference invalid bodies and throw. | **Fixed in branch.** Shared helper requires a non-null, non-array object; handlers use their existing 400 responses. |
| Medium — verification gap | No package lock or unified test command; workflows execute selected suites and side-effect imports. Full discovery found failing contracts absent from routine checks. | **Improved.** Locked dev tools, automatic suite discovery, de-duplication, local network guard and PR CI added. Full-suite failure remains visible. |
| Low — stale test contracts | Root tests expected an old header endpoint, a double-escaped Hive version regex, a sent rather than received Stackbreaker message, and absence of even comments mentioning localStorage. | **Corrected in root tests.** Real guest-session and replay contracts retained; runtime code was not reverted to satisfy obsolete expectations. |
| Low — duplicate browser setup | Twelve suites separately searched for system Chrome and failed with only Playwright's bundled browser installed. | **Consolidated.** One launcher supports pinned bundled headless Chromium, explicit CHROME_BIN or existing CI system Chrome; assertions remain unchanged. |

Authentication behavior change: only explicit invalid membership Authorization credentials now fail closed instead of falling back to cookies. Community key formats, session duration, email recovery protocol, membership pricing/tiers, paid-through logic and payment processing are unchanged. No schema migration is needed.

## 5. Security review and limits

Confirmed controls exercised locally include owner-only route denials, account-scoped deck changes, public profile field selection, device-cookie requirements, recovery-key rotation, revoked membership denial, Ko-fi replay fixtures, DOM injection fixtures and authoritative game replay checks. Input is generally bound as SQL parameters; several public services deliberately do not require an account.

The static scanner flagged `rescue-subscribe.js` HTML-string rendering; the inspected input is a fixed literal form, not untrusted interpolation. It also flagged `/api/site-presence` as unauthenticated; this is an intentional anonymous KV heartbeat, with origin/id/page validation, not a private-data endpoint. Neither pattern alone proves a vulnerability. Quota abuse and KV cost under hostile traffic still deserve separate review.

Items **not verified**: production secret history/rotation, deployed Cloudflare Access exact-email/MFA policy, immutable-alias protection, live second-account permissions, real email deliverability, paid Ko-fi activation/renewals/refunds, concurrent recovery races, malicious-load/rate-limit testing, restore procedures and full production schema parity. No production database was queried to infer sensitive state.

Root middleware currently handles ad-free rendering and presence decoration; the older `docs/SECURITY.md` description of a global cross-site POST gate does not match this source. Individual endpoint origin checks remain. A repository-wide missing-Origin/Sec-Fetch-Site threat-model review is recommended before broadening CSRF behavior. The current CSP is a partial baseline, not a restrictive script-src policy; do not tighten it blindly around Turnstile/ads/embeds.

## 6. Remaining concerns and roadmap

1. **Before merge:** coordinate the protected avatar fixture correction; require the full local suite and PR checks to pass on the exact head. Review the membership rejection change and deck transaction change. No deployment approval is included in this audit.
2. **Before staging mutation tests:** resolve/verify the preview-production D1 sharing described by open issue #74. This is an existing recorded risk, not a newly verified Cloudflare binding observation. Create isolated bindings and test-only secrets only through an approved configuration change.
3. **Next data-integrity batch:** test replacement of challenge entries that already have votes against actual foreign keys; the current `ON CONFLICT ... UPDATE deck_id` path and vote references need an explicit policy for preserving votes. Also exercise recovery races, backend outages mid-enrollment and simultaneous multi-device updates. Do not delete votes or records to make tests green.
4. **Identity/payment operations:** isolated two-user permissions matrix, owner/non-owner MFA, recovery delivery failures, webhook renewals/refunds, device revocation and operator recovery, using approved synthetic identities/provider test modes.
5. **Database maintainability:** inventory deployed schema against the one-off SQL files; define reproducible baseline/migration ordering and test clean install/upgrade/backup restore locally. Production migrations require separate approval.
6. **Frontend quality:** broaden outage interaction tests beyond initial render; add WebKit/iPhone and keyboard/screen-reader checks. Current checks cover overflow/navigation and selected controls, not a complete WCAG audit.
7. **Performance/SEO:** record Lighthouse/Core Web Vitals under controlled network/CPU conditions and real-user data before tuning. Static SEO checks pass, but rankings/indexation, external links, AdSense approval, live TTFB and loading metrics were not comprehensively measured. Atomic batching reduces deck-save DB calls; no quantified speed claim is made.
8. **Documentation/dead code:** label retired Workshop/Binder and password/Stripe paths, then measure references before removing legacy assets. Preserve existing browser data and public URLs. Native Weekly Dispatch still needs its documented consent/provider implementation.
